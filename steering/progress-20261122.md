## 1. `fit.py --draws DIR`

- **What it does.** The fit's random baseline uses the directions written by `evaluation/shared_draws.py` instead of
  its own 100 isotropic vectors, so the fit and the evaluation's nulls use the same vectors.
- **Files:** `steer/draws.py` (new, `load_shared`), `steer/fitting.py` (`fit(..., random_sets=None)`), `fit.py`.
- **Checks before use:** every file against `SHA256SUMS`; the manifest's model, layer, site and dimension against the
  fit's; the manifest's activations hash against the array the fit reads. A failure is a refused run in `search.jsonl`.
- **Recorded:** `fit.json` → `random_source` (directory name, K, families, hashes), and
  `diagnostics.caa.abs_cos_random` (n, max and 95th percentile of |cos| with CAA, per family). `max_abs_cos_random`
  keeps its meaning (the isotropic family). `directions.npz`'s `random` is the shared isotropic family.
- **Decisions:**
  - `--draws` is optional. Draws need the activations, and a fit must stay possible without them (smoke runs, tests).
    Rejected: making them mandatory.
  - The draws are not regenerated by `fit.py`; `shared_draws.py verify` does that. `fit.py` checks hashes only.
  - `--n-random` is ignored with `--draws`; K comes from the manifest.
  - The draws are not excluded from `--exclude-horizons` fits: they are diagnostics, and one shared set was the point.
    This is stated in `fit.py`'s docstring.
  - Not changed: `evaluation/shared_draws.py` reads `L<layer>_<site>.npy` and we write two-digit layers. Same name
    for layers ≥ 10. Noted in `steer/draws.py` and the hand-over document; their code is theirs to change.

## 2. The horizon site

- **What it does.** `extract_horizon.py` reads the residual stream at each token of the stated horizon, at every
  layer, with no baseline run and no generation.
- **Files:** `extract_horizon.py` (new); `steer/sites.py` (`locate_horizon`, `horizon_char_span`); `steer/layers.py`
  (`capture_all`); `steer/activations.py` (format, `horizon_sites`); `steer/hooks.py` (`at_prompt`).
- **Findings while building it:**
  - Gemma 4 and Qwen3.5 split numbers into digits. A horizon has 2 to 7 tokens on `t0_s0`
    (`{2: 94, 3: 204, 4: 187, 5: 72, 6: 106, 7: 8}`), 2,600 in all, the same on both tokenizers.
  - 4 prompts write the horizon's words in an option too (x0042, x0224, x0234, x0311), so the horizon is located in
    the CONSTRAINT line, not by searching the whole prompt.
  - Gemma 4's chat template adds a system turn before the prompt when thinking is on. The first horizon token index
    runs 92–110 with thinking on and 85–103 with it off. So the thinking setting is an input, and is recorded.
- **Decisions:**
  - A separate script, not a site inside `extract.py`: `extract.py` requires a baseline run, and this must not.
  - float32, one file per layer. It is exact for bf16 values and matches the existing arrays. Rejected: one float16
    array (half the size, but not exact for bf16's range, and a second format).
  - Layers 0 .. n by one rule (block outputs; 0 = input of block 1). Layer n is before the final norm, so it is not
    `hidden_states[n]`; documented where it is defined. Rejected: `output_hidden_states`, whose last entry is
    post-norm.
  - The audit is a gate inside the run (nothing is written on a mismatch), not a separate step.
  - Prompts without a horizon get a row with empty lists in `horizon_sites.jsonl`, so rows exist for all 700 uids.
- **For the hook:** `at_prompt(indices)` edits chosen prompt tokens per row, adding each row's left padding;
  `horizon_sites(dir)[uid]` is the row to pass in `rows` (token indices, log-time, option order, label style).
