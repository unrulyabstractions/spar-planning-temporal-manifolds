## 27B run on Vast.ai: throughput collapse diagnosed (cgroup CPU quota)

Status at 05:49 instance time: investment capture done (2000/2000, format 1.000, 40.6 min = 1.22 s/prompt), but the
matrix capture had been crawling since 22:07: 185–195 s per batch of 16 (11 s/prompt), GPU util 1–4%, the capture
process at ~690% CPU and the investment run's background analysis (`analyze.py` sweep) at ~500% CPU for 7.7 h,
still on its first step.
Diagnosis: `/sys/fs/cgroup/cpu.max` = 768000/100000 → a 7.68-core quota while `nproc` = 24. torch/OpenBLAS size
their pools to 24; two such processes (capture + sweep) oversubscribed the quota and the capture's kernel-launching
thread starved. Local control on the 9B: 64 matrix prompts run at the same 3.1 s/batch as 64 investment prompts,
so the prompts are not the cause; prompt lengths are equal (median 135–147 tokens). fla autotune keys do not
include T and the Triton cache stayed at 172 entries, so kernel recompilation is excluded.
Actions: killed the starved analysis (PIDs 4640/4643/4675; to be rerun after the captures) → matrix batches fell to
69–70 s (4.4 s/prompt); installed `.venv/lib/python3.12/site-packages/zz_thread_quota.pth` on the instance setting
OMP/OPENBLAS/MKL/NUMEXPR threads to 4 for every new Python process (verified: torch.get_num_threads() = 4; a
sitecustomize.py was shadowed by the image's own and did not take). The running matrix capture keeps its 24 threads
(restarting would cost as much as letting its remaining 824 prompts finish, ~1 h); every later capture and analysis
gets the cap. Runbook now exports the caps and logs nproc vs quota; CLAUDE.md notes the pitfall.
To do after the chain: rerun `scripts/analyze_run.sh runs/qwen3.5-27b_investment_n2000_s0` and
`within_bin_control.py` (killed), and check that captures 3–5 run at ≈19 s/batch.
